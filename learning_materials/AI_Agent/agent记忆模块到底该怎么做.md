# Agent 记忆模块到底该怎么做

### 内容明确：这次直播不把记忆当成“存储问题”讲，而是当成“状态治理问题”讲。

因为一个真正可用的 Agent 记忆系统，要解决的不是“东西放哪”，而是：

- 什么该记；
- 以什么形态记；
- 谁有权写入长期记忆；
- 新旧记忆冲突怎么办；
- 什么时候该遗忘；
- 压缩错了能不能回放；
- 怎么评估系统而不是越活越脏。

本次直播我们主要讲以下五个方面：

1. 记忆不是上下文窗口不够大的补丁，而是过去的内容如何进入当下。
2. RAG 不是记忆，RAG 解决空间问题，记忆解决时间问题。
3. 向量数据库不是长期记忆的默认底座，只是情景片段层的工具。
4. 真正的架构分水岭是：谁有权写长期记忆，该怎么处理长期记忆。
5. 记忆系统最难的是评估，评的是一个有状态系统在长时间里的演化质量。

### 一句话总结
记忆不是给模型加数据库，而是给一个会行动、会犯错、会被过去影响的系统，加一套管住过去的机制。



# 1. 为什么需要记忆：不是窗口补丁，而是过去如何进入当下

### 理解目标

- 理解上下文窗口只解决“当下装载什么”，不解决“过去如何治理”。
- 区分“保存历史”和“形成可用记忆”。
- 明白不同场景对过去的要求不同：有些要加工成状态，有些必须保留原始证据。

### 需要明白

1、上下文窗口解决的是“这一轮能看见什么”，不是“过去该如何治理”。窗口再大，也不能把三年历史、旧偏好、错误决策、过期事实全部塞进来。

2、记忆的关键不是保存历史，而是决定哪些过去内容该以什么形态进入当下。有些过去要加工成当前状态，有些必须保留原始证据，有些两者都要。

### 内容场景决定如何储存记忆

不要争论“到底要不要保留全部过去”，而是从获取对话内容阶段就要把过去对话信息进行场景分类。

- 有些过去信息需要进行加工记忆，变成当前可用状态。例如：用户个人偏好
- 有些过去信息需要进入原始档案，保留证据链。例如：病例、医生治疗方案、案件证据
- 有些过去信息两条轨都要进，既要有加工结果，也要能回溯到原始证据。例如：技术方案选择

### 一句话总结

上下文窗口再大，也只是更大的当下；Agent 真正需要的记忆，是让过去的信息能被正确地加工、保存、回溯，并在合适的时候进入当下。



# 2. 记忆的二维坐标：不要把“记忆”当成一种东西

### 理解目标

- 掌握记忆的两根正交轴：时间轴和类型轴。
- 明白短期/长期不是类型，事实/事件/情景也不是时间尺度。
- 避免把所有记忆一锅端，或者机械全排列成过度复杂系统。

### 需要明白

- 要把记忆拆成两条正交轴：分别是时间轴和类型轴，先判断记忆要“活多久”，再判断“是什么类型”，避免用一套方案处理所有记忆。
- 时间轴回答“活多久”：短期记忆服务当前任务和回话、当前的几轮推理，长期记忆跨会话存活。
- 类型轴回答“是什么”：结构化事实、实体关系、时序事件、情景片段不是一类东西。
- 时间轴和类型轴是正交的：结构化事实，可以是短期的，也可以是长期的；情景片段也分短期和长期。不要把短期记忆=聊天记录、长期记忆=用户画像，这种说法会把系统设计带偏。
- 设计重点不是先选数据库，而是先判断这条记忆该进入哪个坐标格。

### 记忆问题直觉

- 这两根轴上真正要解决的难题，跟你选什么存储底座基本无关。

- 短期怎么进入长期，这是巩固问题，不是 MySQL 问题。
- 长期记忆怎么避免陈旧，这是衰减和遗忘问题，不是向量库问题。
- 结构化事实怎么防止冲突，这是版本和来源问题，不是换数据库能解决的问题。

### 案例

#### 案例一：

用户说：“这次回答请短一点。”

这是一条短期结构化事实。它影响当前对话，可能只在这一轮或这个会话里有效。你不应该贸然把它写成长期偏好：“用户永远喜欢短回答”。

用户后来又说：“以后和我讲技术问题，默认简洁一点。”

这才更接近长期结构化偏好。它可以跨会话存活，但最好仍然带场景限定：技术问题、默认、简洁一点。

#### 案例二：

用户第一周说：“我住北京。”

用户第四周说：“我搬到上海了。”

如果系统只存一个字段 `city = Shanghai`，那就会丢掉之前所住地址的信息；如果系统只保留两条文本，又不知道哪个是当前状态，也会混乱。

更好的理解是：这是长期时序事件加当前状态。事件层记录“北京 → 上海”的位置变化，档案层当前地址的value是“上海”。

### 一句话总结
记忆不是一坨历史文本，而是时间轴和类型轴组成的坐标系统，先分清它活多久，再分清它是什么，才能避免一锅端。



# 3. RAG 不是记忆：RAG 是空间问题，记忆是时间问题

### 理解目标

- 分清 RAG 和记忆的根本差异。
- 理解 RAG 补 knowledge gap，记忆补 continuity gap。
- 明白成熟记忆系统必须处理冲突、衰减、巩固和遗忘。

### 需要明白
- **RAG 是空间问题**：外部知识够不够广，能不能查到公司制度、产品文档、API、论文。RAG 补 knowledge gap：模型不知道什么，就去外部资料里找
- **记忆是时间问题**：能不能将相关记忆正确的应用到现在，比如过去互动、用户偏好、项目决策、状态变化、状态演化。记忆补 continuity gap：系统不能每天像失忆的金鱼一样，忘记“我们之间发生过什么”。
- **记忆**：天生带噪声，天生会过期，天生会互相矛盾

- **写入 + 检索不等于成熟记忆**：成熟记忆还要处理冲突、过期、巩固、衰减和遗忘。
- **成熟的记忆系统的难点在哪？**难在写进去以后怎么治理，真正把 **记忆** 和 **检索** 区分开的，是遗忘和巩固
- **小心工程幻觉**：切记不要理解成只要有一个数据库，能 insert，能 search，就有记忆了



### 一句话总结
RAG 让 Agent 查到更广的知识，记忆让 Agent 正确地带着过去信息在未来被正确的使用；前者是空间检索，后者是时间治理。



# 4. 长期记忆该用向量数据库吗

### 理解目标

- 知道向量库的主场和边界。
- 掌握异构存储 + 混合检索的基本设计。
- 避免用语义相似度处理精确事实。

### 需要明白

- **结论：**向量库不是长期记忆的默认底座，只是待选项，不是默认项。
- 结构化事实要按 `key` 精确查，不该靠相似度猜。
- 实体关系的内容最重要的是保留图结构或关联查询，不能被向量打平。
- 时序事件要保留时间线、版本、最近性（recency）、是否取代（supersede）。
- 向量库真正适合的是“情景片段”——说不清 key、但语义上可能相关的内容。

### 一句话总结
长期记忆不要默认接向量库，向量库只适合语义模糊的情景片段；真正决定成败的，是按记忆的类型分层和后续记忆治理策略。



# 5. 真正的需要考虑的难题：巩固、背压、一致性、注入、遗忘与压缩

### 理解目标

- 理解短期和长期是两套系统，中间必须有巩固管线。
- 掌握巩固触发、背压、一致性、注入、输入输出不对称、重要性、遗忘、有损压缩等关键问题。

### 需要明白

- **巩固是核心管线**：短期记忆像 WAL，巩固管线是checkpoint，长期记忆是 checkpoint后的数据；巩固成功前，短期原文不能被提前删除。

##### 存储记忆时的难题：

- **该怎么做巩固？**：token 快满、会话结束、后台定时三个任务不是分别三个执行者，而是一个执行者加三个唤醒信号。
- **背压需要解决“内容过载巩固不过来了怎么办”**：当输入速度大于巩固速度，进行分块消化、降采样、先抢救摘要，再丢低价值细节，约束高代价保险丝类型数据等方式。
- **输入输出的处理方式不对称**：长期记忆主要从用户输入、工具结果、承诺和决策中抽取；不要原样保存 assistant 的话术进行存储。
- **巩固必然有损压缩**：要保留限定词、来源、置信度等。
- **记忆重要性没有单一指标**：记忆的重要性判定并不依靠单一指标，也依靠类型、场景、代价等判定标准。
- **遗忘不是 TTL delete**：遗忘应是巩固、衰减、归档、兜底删除的组合。

##### 读取记忆时的难题：

- **记忆读取一致性要分场景**：同会话靠短期 WAL 兜底；跨会话可接受短暂 stale（陈旧的记忆），但健康、安全、身份、权限、金额要走快速通道。
- **对话时记忆分层注入**：注入的是巩固后的高密度结论，而不是原始对话情景的流水信息。

### 一句话总结
Agent 记忆真正难的不是保存过去，而是把过去经过巩固、背压、一致性控制、遗忘和有损压缩后，安全地变成未来可用的状态。
